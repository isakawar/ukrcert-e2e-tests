# E2E УкрСертифікація — іноземні користувачі: архітектура і план

Мета: автоматизувати e2e-сценарії з тест-плану (вкладка «Тест-кейси»: REG, MOD, AUTH, EXAM, ADMIT, PROFILE, REGR)
на Playwright + TypeScript зі звітом Allure. Принцип — без over-engineering: лише ті шари, які реально
знімають біль саме цієї фічі (кілька ролей, листи з кодами, гео-визначення, довгі передумови).

## 1. Що робить цю фічу складною для e2e

| Проблема | Рішення в проєкті |
| --- | --- |
| Кілька ролей в одному сценарії: іноземний користувач, адміністратор (модерація), відповідальний за пункт тестування (допуск) | Окремий `BrowserContext` на кожну роль у межах одного тесту; сесії адміна/відповідального зберігаються один раз у `setup`-проєкті (`storageState`) |
| Частина флоу живе в пошті: посилання активації, одноразовий код (10 хв), причина відмови | `MailClient` + провайдер: Maildrop (публічні скриньки без реєстрації, GraphQL API) або Mailpit; кожен тест генерує власну адресу |
| Функціонал вмикається лише для не-українського IP | `GEO_MODE` у конфігу: `proxy` (реальний закордонний проксі/VPN) або `header` (тестовий заголовок-оверрайд, якщо бек його підтримує) або `none` (раннер уже за кордоном) |
| Довгий ланцюг передумов (реєстрація → модерація → активація → логін) перед більшістю кейсів | Не більше 2 заявок за прогін: заявка A (схвалення) і B (відмова) проходять свої кейси по черзі, стан — у `runState`; наступні етапи беруть схваленого заявника A (`approvedUser` → `loggedInUser`) |
| Валідація файлів документа (PDF, DOCX, зображення; ліміт розміру невідомий) | Невеликі реальні файли в `src/data/files`, «завеликий» файл генерується в пам'яті під `MAX_UPLOAD_MB` |

## 2. Стек

- `qas-cli` — синхронізація кейсів і завантаження результатів у QA Sphere (офіційний CLI, версію закріплено).
- `@playwright/test` + TypeScript — раннер, фікстури, трейси, паралелізм «з коробки».
- `allure-playwright` + `allure` (Allure 3, без Java) — звіт з історією, категоріями падінь, прив'язкою до ID кейсів.
- `dotenv` — конфіг оточень. `eslint` + `typescript-eslint` + `eslint-plugin-playwright` — ловить пропущені `await`, найчастіший баг у Playwright-тестах.

Свідомо НЕ беремо: BDD/Cucumber, власні обгортки над Playwright, окремий DI, Selenium Grid/оркестрацію контейнерів — поки не з'явиться реальна потреба.

## 3. Структура

```
e2e-ukr-cert/
├── PLAN.md                    ← цей файл
├── README.md                  ← як запустити
├── playwright.config.ts       ← проєкти: setup, foreign, ua
├── allurerc.mjs               ← назва звіту, історія, групування
├── .env.example
├── src/
│   ├── config/env.ts          ← читання та перевірка змінних оточення
│   ├── pages/                 ← Page Objects: лише локатори + дії, без бізнес-перевірок
│   │   ├── user/              ← вхід/реєстрація, OTP-логін, іспити, профіль, проходження іспиту
│   │   └── admin/             ← модерація, пункти тестування, допуск
│   ├── flows/                 ← багатокрокові бізнес-дії поверх pages (зареєструвати, погодити, активувати…)
│   ├── services/mail/         ← MailClient + реалізація
│   ├── fixtures/index.ts      ← розширений `test`: ролі, пошта, стани користувача
│   ├── data/                  ← фабрики тестових даних + файли документів
│   └── reporting/allure.ts    ← хелпер `tc()` — мітки Allure з ID кейсу
└── tests/
    ├── setup/                 ← логін адміна/відповідального → .auth/*.json
    ├── registration.spec.ts   ← REG (без створення заявок)
    ├── journey.spec.ts        ← заявка A: REG-05/13/17/04, MOD-01…03, AUTH
    ├── moderation.spec.ts     ← заявка B: MOD-04…07
    ├── exam-registration.spec.ts ← EXAM
    ├── admission.spec.ts      ← ADMIT
    ├── profile.spec.ts        ← PROFILE
    └── regression-ua.spec.ts  ← REGR (український флоу, smoke)
```

Правило шарів: `tests → fixtures/flows → pages`. Тест читається як тест-кейс з документа; локатори живуть
лише в `pages`, тож після інспекції dev-оточення правки будуть точковими.

## 4. Проєкти Playwright

| Проєкт | Гео | Що запускає |
| --- | --- | --- |
| `setup` | — | логін адміна і відповідального, збереження `storageState` |
| `foreign` | закордонний IP (`GEO_MODE`) | усі спеки з тегом `@foreign` |
| `ua` | звичайний (український) IP | спеки з тегом `@ua`: REG-02, EXAM-02, REGR |

## 5. Теги та відбір

- `@smoke` — наскрізний happy path (реєстрація → модерація → активація → OTP → іспит → допуск), ганяємо на кожен деплой.
- `@regression` — усе інше.
- `@slow` — кейси з реальним очікуванням (AUTH-05: спливання коду через 10 хв). За замовчуванням виключені, окремий нічний прогін.
- `@blocked` — кейс, для якого ще немає способу перевірки в e2e (див. розділ 7); у звіті видно як skipped з причиною.

## 6. Allure: що робимо «кастомно»

- Ієрархія: epic «Іноземні користувачі» → feature (область: Реєстрація, Модерація…) → story (ID кейсу).
- Кожен тест має TMS-посилання на тест-план і мітку `caseId`, severity, owner — через один хелпер `tc('REG-05', {...})`.
- Вкладення: отримані листи (активація, код, відмова) як HTML, завантажений документ, trace/скрін/відео на падіннях.
- Категорії падінь: «Дефект продукту» (assertion), «Нестабільний локатор» (timeout на локаторі), «Інфраструктура: пошта»
  (лист не прийшов), «Інфраструктура: гео» (функціонал для іноземців не ввімкнувся).
- Environment-блок: оточення, base URL, GEO_MODE, браузер, версія збірки (якщо передана).
- Історія/тренди між прогонами (`allure-history.jsonl`).

## 7. Відомі обмеження (обговорити з командою)

- AUTH-05 (код прострочений): чекати 10 хв у CI дорого → попросити dev-налаштування TTL коду (напр. 30 с) для тестового оточення.
- ADMIT-05/06 (передача в РДС): e2e бачить лише UI платформи → потрібна точка спостереження (статус у UI, лог в адмінці або API).
- REGR-01 (вхід через Дію): зовнішня держ-авторизація не автоматизується → перевіряємо лише, що кнопка Дії є і веде на правильний домен.
- ADMIT-02/04 (старт іспиту): ймовірно, іспит можна почати лише в час таймслоту → на dev потрібен слот «зараз» або вимкнена перевірка часу.
- EXAM-02/03, REGR-02 потребують залогіненого українського користувача, а вхід лише через Дію → сесію знімаємо вручну один раз (`UA_USER_STORAGE_STATE`), без неї кейси skipped.
- Відкрите питання до вимог: що відбувається, якщо ввести email заявки, яка ще на модерації (акаунта ще немає → чи можна подати дублікат?).
- Ліміт повторних відправок коду та максимальний розмір файлу — ще не визначені вимогами; параметризовано через `.env`.
- Локатори написані за назвами полів із вимог (UI лише українською) і мають бути звірені з dev-оточенням.

### Етап 2 (модерація, вхід за кодом) — що з'ясовано на dev, 23.09

- Модератор входить за паролем на **lms-exam-dev** (`ADMIN_BASE_URL`), а не на foreign-dev; меню → «Заявки на реєстрацію іноземців» (`/foreign/registration/review/`, вкладки Очікує перевірки / Схвалено / Відхилено / Новий документ очікує перевірки).
- Схвалення створює акаунт LMS `foreign_<id>` (видно через `/api/user/v1/accounts?email=` під модератором), відмова — ні. Документ модератор завантажує як вкладення; без сесії → редирект на вхід.
- ❗ **Dev не надсилає листи**: і «Заявку схвалено», і «Відхилення заявки» в таблиці «Повідомлення про рішення» → «Не вдалося надіслати» (перевірено і для Maildrop, і для іншого поштового домену, «Надіслати повторно» теж не допомагає); лист з одноразовим кодом не приходить. Тому MOD-03, MOD-04 (частина з листом) і AUTH-01…04 зараз падають з `[mail]` — це дефект оточення, решта перевірок у цих кейсах проходить.
- ❓ Розбіжність з вимогами: сторінка статусу схваленої заявки каже «Тепер ви можете увійти за одноразовим кодом», а вимоги (п. 3.1) — що спершу треба активувати акаунт за посиланням з листа. Чи є посилання активації — стане видно, щойно запрацює пошта (AUTH-01/02).
- ❓ Email відхиленої заявки на кроці 1 реєстрації блокується («Не можна продовжити…»); подати повторно можна лише зі сторінки статусу («Виправити та подати повторно») — тобто лише маючи посилання на неї. Повторна подача оновлює ту саму заявку (історія документів), а не створює нову.
- ✅ HTML в імені (`<b>Smith</b><script>…`) екранується і в списку, і в заявці (MOD-07).
- Вхід за кодом: для будь-якого email (і неіснуючого) відкривається крок з кодом — акаунти не розкриваються (AUTH-07); код — 6 цифр; неправильний і прострочений код дають один текст «Одноразовий код недійсний або строк його дії минув.».

### Прибирання тестових даних — потрібно від розробників

`npm run cleanup -- --dry-run` уже знаходить тестові заявки (усі вкладки модерації) і їхні акаунти, лише для адрес `^ukrcert-[a-z0-9-]+@maildrop\.cc$`. Видалити їх зараз нема чим:

- Open edX на dev — гілка Juniper: `/api/user/v1/accounts/retire/`, `…/retirement_queue/`, `…/{username}/deactivate/` існують (401), але bulk-retire endpoint-а немає, а `retire` працює лише для користувачів, уже поставлених у чергу вилучення (для цього потрібен пароль користувача — у іноземців його немає — або management-команда на сервері). OAuth-клієнта для тестів немає (`/oauth2/access_token/` → `invalid_client`), модератор `tec1` — не staff.
- Для заявок фічі (ще не акаунтів) API немає зовсім — ні видалення, ні списку в JSON.

Що попросити (варіант 1 — найпростіший для CI): dev-only endpoint, напр. `POST /foreign/registration/e2e-cleanup/` для OAuth2 client-credentials клієнта, що за списком email (сервер теж перевіряє шаблон `ukrcert-*@maildrop.cc`) видаляє заявки, документи, повідомлення і вилучає пов'язані акаунти (retire). Варіант 2 — стандартний шлях Open edX: сервісний користувач `RETIREMENT_SERVICE_WORKER_USERNAME` + OAuth2 client (client_credentials, JWT) + спосіб поставити користувача в чергу вилучення без пароля, і окремо — видалення заявок. Після цього: реалізувати видалення в `scripts/cleanup.mjs`, `globalTeardown` (вимикається `CLEANUP=0`), крок у GitHub Actions, секрети клієнта.
